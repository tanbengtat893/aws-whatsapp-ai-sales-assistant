# Delivery, Measurement and Controls — WhatsApp Sales Enquiries Assistant

How the proposal works safely and how success is measured.

The system is built around one guiding principle from the spec: **people before technology.** The bot only shortcuts repetitive, clearly-answerable questions; whenever confidence is low or a customer asks for a person, the enquiry routes to a human rep rather than to a silent wrong guess.

## Data, Tools & Operating Constraints

### Data or Documents

| Data / Document | Source | Owner | Access Status | Privacy or Quality Concern |
|-----------------|--------|-------|---------------|-----------------------------|
| Customer enquiry messages (`from`, `text`, timestamp) | Inbound WhatsApp webhook (simulated chat page in phase 1) | Puay Sim (Sales Ops) | Restricted — server-side store only | Contains customer-authored text; sanitized before storing (Req 1.3); store only what is needed to answer/escalate (NFR: privacy) |
| FAQ knowledge base (intents, keywords, answers in en/ms/zh) | Authored by reps/admin; seeded starter set | Noel (Content Admin) | Read by bot, write via FAQ admin API | Quality risk: wrong or outdated answers mislead customers; English answer mandatory (Req 6.3) |
| Enquiry records (language, confidence, status, matched FAQ) | Generated by the app pipeline | Alvin (Project Owner) | Internal (dashboard + store) | Derived personal data; retained only as needed; no secrets in the record |
| Escalation records (enquiry id, reason, status) | Generated on escalation | Puay Sim (Sales Ops) | Internal (dashboard) | Operational data; low sensitivity |
| Configuration & secrets (`.env`: tokens, thresholds) | Project owner | Alvin (Owner) / Peter (DevOps) | Secret — never committed (`.gitignore`) | Must stay out of the repo (NFR: privacy); leaked WhatsApp token = account takeover risk |

### AI Models & Tools

| Model / Tool | Role in the Proposal | Operating Constraint |
|--------------|----------------------|----------------------|
| `franc-min` (language detection library) | Detects enquiry language, limited to en/ms/zh with a confidence score | Below `LANG_MIN_CONFIDENCE` (0.5) defaults to English; runs locally, no external calls |
| Keyword/intent FAQ matcher (v1, in-house) | Matches enquiry to a stored FAQ intent and produces a match confidence | Below `FAQ_MIN_CONFIDENCE` (0.6) escalates to a human; deterministic, no AI in v1 |
| Simulated WhatsApp sender | Records outbound replies in-store and returns them in the webhook response (phase 1 demo) | No external API calls; used while Meta approval is pending (Req 7.1) |
| WhatsApp Business Cloud API (phase 2) | Sends real replies to customers; Meta webhook verification | Requires Meta Business approval + tokens; selected only when `WHATSAPP_MODE=cloud`; rate/policy limits apply |
| OpenClaw / LLM matcher (optional, week-3 stretch) | Smarter FAQ matching behind the same `match()` interface, only if it measurably improves answers | Added only where it beats keyword matching; still gated by the same confidence-to-escalate rule; human-in-the-loop preserved |

### Agent / Workflow Roles

| Role | Responsibility | Input | Output | Escalate When |
|------|----------------|-------|--------|----------------|
| Webhook controller | Receive, validate, sanitize, and record the enquiry | `{ from, text }` payload | Persisted enquiry record; kicks off pipeline | Missing `from`/`text` → reject with 400, no record (Req 1.2) |
| Language service | Detect the customer's language | Sanitized enquiry text | `{ language, confidence }` | Confidence below threshold → default to English (not a human escalation) |
| FAQ service | Match enquiry to a stored FAQ answer | Text + detected language | `{ matched, faqId, answer, confidence, fallbackLanguageUsed }` | No answer in detected language → English fallback flagged |
| Escalation service | Decide auto-answer vs hand off to a person | FAQ match result + text + language | `{ escalate, reason }` | No confident FAQ match → `low_confidence`; explicit human request → `human_requested` |
| Sender (simulated/cloud) | Deliver the reply or acknowledgement | Recipient + message | `{ delivered, channel }` | Delivery error → logged, enquiry set pending for a rep |
| Human sales rep (Puay Sim, lead) | Handle escalated enquiries via the dashboard | Escalated enquiry detail + reason | Resolution + status update (who resolved it) | Anything the bot could not confidently answer |
| Admin (Noel) | Maintain FAQ answers in each language | New/edited FAQ content | Updated FAQ used by subsequent enquiries | FAQ without English answer → rejected (Req 6.3) |

### Integrations and Manual Fallback

- **WhatsApp channel (swappable):** the `sender` interface has two implementations — `simulated` (in-store, no external calls) and `cloud` (real WhatsApp Business Cloud API). Switching modes needs no change to language/FAQ/escalation logic (Req 7.3). If the Cloud API is unavailable, the app can fall back to `simulated` mode so development and testing continue.
- **Language detection failure:** if detection is uncertain, the system defaults to English rather than guessing wrong.
- **FAQ matching failure / uncertainty:** any enquiry the bot cannot confidently answer is escalated to a human rep with a localized acknowledgement to the customer — the core manual fallback.
- **Answering error:** an error while handling one enquiry is caught, logged server-side, and results in an escalation (safe fallback), never a crash that blocks other enquiries (NFR: reliability, humane fallback).
- **Data store:** JSON/SQLite behind a `store` interface; can be swapped for a managed DB later without touching business logic.

## Success Measures

| Metric | Baseline | Target | How Measured | Review Period |
|--------|----------|--------|--------------|---------------|
| Auto-answer rate (enquiries resolved by bot without a rep) | 0% (all handled manually today) | 50–60% of common enquiries auto-answered | Count `auto_answered` vs total enquiries in the store/dashboard | Weekly |
| Correct-language reply rate | Manual, inconsistent | ≥ 95% of replies in the customer's detected language (or flagged English fallback) | Compare detected language vs reply language in enquiry records; sample review | Weekly |
| Escalation accuracy (uncertain items correctly handed off) | No formal handoff | 100% of low-confidence / human-requested enquiries escalated, 0 silent wrong guesses | Audit escalation records against enquiry outcomes | Weekly |
| First-response time to customer | Minutes–hours (rep availability) | Instant auto-reply; escalations acknowledged immediately | Timestamp difference between `receivedAt` and reply | Weekly |
| Rep time saved on repetitive questions | Full manual load | Measurable reduction as auto-answer rate rises | Auto-answer count × avg handling time saved | End of each milestone |
| Test suite health | None | 100% of unit + integration tests passing on every change | `npm test` (language, FAQ, escalation units + webhook integration) | Every commit / CI run |
| Deployment reachability (final milestone) | Not deployed | Chat page, dashboard, and webhook reachable at server public IP | Manual check + webhook echo response (Req 8.2) | Final milestone |

## Risks, Guardrails and Human Approval

### Risks and Controls

| Risk | Consequence | Preventive Control | Human Owner |
|------|-------------|--------------------|-------------|
| Bot gives a confident but wrong answer | Customer misled; lost trust/sales | Confidence threshold (`FAQ_MIN_CONFIDENCE` 0.6); below it always escalates; English-required FAQ validation | Noel (Content Admin) |
| Wrong language detected | Customer gets a reply they can't read | `LANG_MIN_CONFIDENCE` default-to-English; English fallback flagged for review | Alvin (Project Owner) |
| Outdated / incorrect FAQ content | Repeatedly wrong auto-answers at scale | FAQ admin API with edit history (`updatedAt`); periodic content review; reps can correct via dashboard | Noel (Content Admin) |
| Secrets leaked (WhatsApp token, keys) | Account takeover, message spoofing, data exposure | Secrets in `.env`, never committed (`.gitignore`); `.pem` key locked to owner-only permissions; no secrets in enquiry records | Peter (DevOps) / Alvin (Owner) |
| Customer PII over-collected or over-retained | Privacy breach, compliance exposure | Store only what's needed to answer/escalate; sanitize input; no unnecessary retention (NFR: privacy) | Alvin (Project Owner) |
| Server compromise / open ports | Unauthorized access to app or data | Only the app port opened in Lightsail firewall; SSH via key only; keep OS patched | Peter (DevOps) |
| One enquiry error crashes the service | All customers blocked | Per-enquiry error handling → escalate + log, never crash; error details never returned to callers | Alvin (Project Owner) |
| Prompt/message injection (esp. if LLM added) | Manipulated or unsafe replies | Treat customer text as untrusted; keyword matcher is deterministic; LLM stretch goal still gated by confidence-to-escalate and human review | Alvin (Project Owner) |
| WhatsApp API policy violation (phase 2) | Number blocked by Meta | Follow WhatsApp Business policy; use approved templates; keep opt-in records | Alvin (Project Owner) |

### Human Approval Points

- **Go-live to real WhatsApp (`WHATSAPP_MODE=cloud`):** **Alvin (Project Owner)** sign-off required before switching from simulated to the live customer channel.
- **FAQ publication/edits:** **Noel (Content Admin)** reviews and approves new or changed answers before they are used by the bot.
- **Firewall / server changes:** **Peter (DevOps)** approves any port opening or configuration change on the Lightsail instance.
- **Escalation resolution:** **Puay Sim (Lead Rep)** or another rep reviews and closes every escalated enquiry; the system records who resolved it (Req 5.3).
- **Adding the LLM/OpenClaw matcher:** enabled only after it demonstrably improves answers on a test set, with **Alvin's** approval; human-in-the-loop escalation stays in force.
- **Handling of any customer complaint or sensitive case:** always routed to a person, never auto-closed.
